## 2026-10-31T23:50:00+01:00 — CDC-3 — API de résolution des codes et des étiquettes de pièces

- **Agent** : api (lot CDC-3) · **Branche** : `lot/api/CDC-3-qr-pieces` (base `06f2fd0`, `lot/fe/CDC-0-socle-ui`) · **Commit** : voir `git log`
- **Statut** : fait ; tests de contrat avec base écrits, non lancés (voir Reste)
- **Quoi** : remplace le squelette 501 de `/api/part-scans` par deux routes en lecture seule, derrière le drapeau `part-qr` (coupé par défaut). `GET /resolve?code=` : code scanné -> `{ id, reference, name, quantity, location, unit }`, rôles `PART_SCAN_ROLES` (admin, warehouse, workshop_manager, technician). `GET /labels?ids=1,2,3` : `{ items: [{ partId, payload, reference, name, location, unit }], missingIds }`, rôles `PART_LABEL_ROLES` (admin, warehouse), garde `authorize` propre au routeur. Le client reçoit 403 aux deux ; aucun prix, fournisseur ni description dans aucune réponse.
- **Comment** :
  - `shared/contracts/part-scans.ts` : chemins, constantes (`PART_SCAN_QUERY_KEY` = `c`, `PART_SCAN_CODE_VERSION` = 1, bornes), schémas Zod des requêtes (`code` 1 à 300 caractères ; `ids` entiers stricts, dédoublonnés, 100 au plus, jamais tronqués) et des réponses (`strict` : un champ en trop, un prix par exemple, fait échouer la réponse au lieu de fuiter).
  - `server/lib/part-scan-code.ts` (pur) : `buildPartScanPayload(id)` -> `/inventory/scan?c=FM1:<id>` ; `parseScanCode(texte, formats)` essaie une liste de `ScanCodeFormat` (`fleetmasterFormat`, puis `referenceFormat`). Tolère espaces, casse, chiffres pleine chasse, `%3A`, URL absolue ou sans protocole d'un hôte quelconque, y compris derrière un préfixe de chemin. Refuse : autre protocole que http(s), autre page, clé `c` répétée, version inconnue (`FM2:` ne retombe pas en référence), zéros en tête (une pièce = un seul code), identifiant hors int32, caractères de contrôle, texte de plus de 300 caractères. Ne lève jamais.
  - `server/services/part-scans-service.ts` : `db.select` avec les six colonnes énumérées (`unit_price`, `supplier` jamais lus), `limit(2)` pour détecter l'ambiguïté. Référence : `upper(btrim(reference)) = upper(btrim(:code))`, l'expression de l'index `parts_reference_key_idx`. Table `FINDERS` typée par format : ajouter un format à `ScannedCode` sans sa recherche ne compile plus.
  - Erreurs : `AppError` 400 (code illisible ; validation Zod), 404 (aucune pièce), 409 (référence portée par plusieurs pièces, qui ne diffèrent que par la casse : la contrainte unique y est sensible). `cause` pour les logs, jamais dans la réponse. Logs `moduleLogger("part-scans")` avec `requestId`.
  - Tests du socle modifiés, uniquement pour `part-scans` : voir « Tests modifiés ».
  - Choix de format (reuse-first) : Build pour la charge utile (une URL relative versionnée d'environ 25 caractères, aucun équivalent à adopter : un format tiers n'apporterait pas la version ni la cloison par chemin) ; Adopt pour le rendu : `qrcode` (déjà au `package.json` du socle), côté client. Pas de recherche en ligne : décision locale de faible portée.
- **Pourquoi** : lot #3 du cahier des charges (étiquettes imprimées par le magasin, scan par les quatre rôles). La charge utile ne porte que l'identifiant : une étiquette perdue ne révèle rien, et le prix d'achat qui fuit déjà sur `GET /api/parts/:id` (`routes.ts`, gelé) n'est pas reproduit.
