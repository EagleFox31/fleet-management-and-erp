# ADR 0001 — Conventions du lot « recette du 2 novembre 2026 »

- **Statut** : accepté le 30 octobre 2026
- **Portée** : tout le code produit pour la recette client du lundi 2 novembre 2026
  (fonctionnalités P-01 à P-26, tâches T-01 à T-65).
- **Registre associé** : [registre-proprietaires.md](registre-proprietaires.md), propriété des
  fichiers et fenêtres de fusion, à lire avant chaque PR.

## Contexte

Le lot est développé en parallèle par plusieurs agents (deux par spécialité : base de données,
backend, API, frontend ; un architecte ; un agent produit) pendant qu'une autre session corrige
l'existant par les tests. Sans conventions figées avant le parallélisme, chaque agent invente ses
codes d'erreur, ses noms de route et ses migrations, et les PR entrent en conflit sur les mêmes
fichiers.

Cet ADR fige ces conventions. Il complète `AGENTS.md`, qui reste la référence pour tout ce qu'il
ne redit pas.

## Décision

### 1. Architecture : tranches verticales dans le monolithe

On garde Express + Drizzle + React. Pas de nouveau service, ni de file de messages, ni de base
séparée. Une fonctionnalité est une tranche verticale dans ses propres fichiers :

| Couche | Emplacement | Règle |
|---|---|---|
| Contrat | `shared/contracts/<domaine>.ts` | Schémas zod `…Request`, `…Query`, `…Response`, constantes de chemin, types inférés. Seule source de vérité HTTP, importée par le serveur et le client. Dérivé du schéma Drizzle par `.pick` / `.omit`, jamais réexporté tel quel. |
| Routeur | `server/api/<ressource>.routes.ts` | Valide par le contrat, délègue au service. Un fichier par ressource. |
| Garde de rôle | `server/api/index.ts` | Posée **au montage** du routeur, pas route par route. |
| Service | `server/services/<domaine>-service.ts` | Logique métier sans HTTP. Les règles pures (chevauchement, échéance, verrouillage) sont des fonctions sans E/S. |
| Intercepteur | `server/middleware/<nom>-guard.ts` | Comportement ajouté devant une route historique de `routes.ts` sans la modifier (§2). |
| Tâche de fond | `server/jobs/<nom>.ts` | Enregistrée dans `startBackgroundJobs()` (`server/scheduler.ts`), exécutée sous `pg_try_advisory_lock`, rattrapable au démarrage. |
| Écran | `client/src/pages/<domaine>/…` | Hooks typés par le contrat, accès par `useFeature` / `<FeatureGate>`, erreurs par `userMessageOf`. |

Fichiers que l'équipe du lot ne modifie pas : `server/routes.ts`, `server/storage.ts`,
`server/_archive/`, et les tests existants (propriété de la session de tests).

### 2. Intercepteurs plutôt que modification de `server/routes.ts`

`server/app.ts` monte `app.use("/api", apiRouter)` avant `registerRoutes(app)`. Un middleware de
`apiRouter` qui appelle `next()` s'exécute donc devant les routes historiques.

- Verrouillage (P-03) et captcha (P-26) : `loginLockoutGuard` sur `POST /auth/login` et
  `POST /auth/pin-login`. Le compteur porte sur le nom saisi, même inconnu, pour ne pas révéler
  l'existence d'un compte. Il réagit à la réponse par `res.on("finish")` : 401 incrémente, 200 remet
  à zéro.
- Double affectation (P-08) : `bookingGuard` sur `/work-orders`, monté avant les autres routeurs
  `/work-orders`.
- Journal d'audit (P-04) : `auditWrites(config)`, déclaratif (motif de chemin → `entityType`),
  écrit `activity_logs` après une réponse < 400 sur une écriture, sans bloquer la réponse, clés
  sensibles masquées (`password`, `pin`, `token`, `*secret*`).

### 3. Contrat d'erreur

On reprend `shared/errors.ts` **sans nouveau code**. Le serveur lève
`AppError(status, messageUtilisateur, { cause })` (`server/lib/app-error.ts`).

| Situation | Statut | Code |
|---|---|---|
| Corps ou paramètre invalide, captcha absent ou faux | 400 | `VALIDATION` |
| Rôle refusé, ou objet hors périmètre client (`canAccessOwned`) | 403 | `FORBIDDEN` |
| Drapeau de fonctionnalité coupé, objet inexistant | 404 | `NOT_FOUND` |
| Double affectation, doublon métier | 409 | `CONFLICT`, avec un message métier explicite (pas le message par défaut) |
| Compte verrouillé | 429 | `RATE_LIMITED`, avec `lockedUntil` |

Jamais `error.message`, SQL ni stack dans une réponse. Logs par `moduleLogger("<module>")`, aucun
`console.*` dans du code neuf (AGENTS.md §10).

### 4. Routes

- Préfixe `/api`, ressources en kebab-case au pluriel.
- Action métier : `POST /api/<ressource>/:id/<verbe>` (`receive`, `validate`, `quality-check`,
  `unlock`).
- Administration : `/api/admin/*`.
- Avant de créer un chemin, le chercher dans `server/routes.ts` : Express sert la première
  déclaration, un doublon masquerait la nouvelle route.
- Route ouverte à un client : `isAnyUser`. Route réservée au personnel : `isStaff`
  (`server/middleware/auth.ts`). Rôles importés de `shared/constants/roles.ts`, jamais redéclarés.

### 5. Migrations idempotentes

- Un seul fichier `server/db/migrations/20261031_lot_recette.sql`, dupliqué dans
  `server/init-database.ts` (`CREATE TABLE IF NOT EXISTS`, `ALTER TABLE … ADD COLUMN IF NOT EXISTS`).
- Interdits : colonne `NOT NULL` sans `DEFAULT`, `DROP`, `ALTER TYPE` destructif.
- Référentiels insérés en `ON CONFLICT DO NOTHING`.
- Contraintes posées dans un bloc `DO` protégé, après contrôle en lecture seule des données
  existantes (T-63) : une contrainte qui échoue sur l'existant ne bloque pas le démarrage.
- Critère vérifiable : un second démarrage sur une base déjà migrée n'écrit rien (test
  d'intégration T-07).
- Après la PR de schéma (T-07), toute colonne passe par une PR d'amendement DB.

### 6. Drapeaux de fonctionnalité

- Clés en kebab-case, déclarées **seulement** dans `shared/feature-flags.ts` avec leur niveau
  (`must`, `should`, `later`) et leur valeur par défaut.
- Valeurs surchargées par la variable d'environnement `FEATURE_FLAGS`
  (ex. `incidents=on,fuel-prices=off`), résolues par `server/lib/feature-flags.ts`.
- Défauts : `must` actif, `should` et `later` coupés. Un SHOULD fusionné n'est activé qu'après
  validation en répétition générale (T-59).
- Exposition : `GET /api/feature-flags` (`isAnyUser`). Garde serveur `requireFeature(key)` → 404.
  Côté client : `useFeature(key)`, `<FeatureGate>`, champ `feature?` des entrées de menu.
- Tout endpoint SHOULD porte `requireFeature`.
- Le drapeau `exports` coupe les 8 routes d'export si la correction P-01 échoue (coupe-circuit).
- Le gel du code (dimanche 20 h) n'est pas un gel de configuration : activer ou couper un drapeau
  demande une variable et un redémarrage, sans redéploiement.

Clés du lot :

| Niveau | Clés |
|---|---|
| `must` | `exports` |
| `should` | `work-order-audit-trail` (P-13), `vehicle-cost-summary` (P-14), `tire-movements` (P-15), `part-requirement-receive` (P-16), `fuel-vouchers` (P-17), `fuel-anomalies` (P-18), `fuel-prices` (P-19), `time-tracking` (P-20), `pending-invoices` (P-21), `incidents` (P-22), `oil-change-prefill` (P-24), `quality-check` (P-25), `captcha` (P-26) |
| `later` | `email-notifications` (P-23), `finance`, `report-schedules`, `qhse`, `gps`, `pricing` |

### 7. Événements temps réel

- Noms en snake_case `<entité>_<participe passé>` (`incident_reported`), déclarés **seulement**
  dans `shared/contracts/realtime-events.ts`.
- Émission par `broadcastUpdate(event, data)` (global défini dans `server/index.ts`). La portée
  est explicite dans `data.scope` : `{ type: "roles", roles: [...] }` ou `{ type: "user", ... }`.
  `broadcast` est réservé aux référentiels.
- Charge utile minimale (`{ id, … }`) : le client ré-interroge.
- Un seul consommateur côté client : `client/src/hooks/useRealTimeSync.ts`.
- Toute transition applique la règle des 3 couches (AGENTS.md §2) et a un test temps réel à deux
  comptes de rôles différents qui vérifie la trame WebSocket (AGENTS.md §3).

### 8. Tests

Pyramide dans `tests/` et `e2e/` uniquement, jamais colocalisés :

1. unitaire pour les règles pures ;
2. intégration pour les services, sur `DATABASE_URL_TEST` ;
3. contrat HTTP en processus, avec la matrice des rôles (c'est le niveau « API ») ;
4. e2e Playwright (`node node_modules/@playwright/test/cli.js`), fichiers `e2e/1x-*.spec.ts`.

Les tests du lot sont dans des **fichiers nouveaux** : on n'édite pas les suites existantes. Les
e2e (T-37, T-55) sont confiés à l'agent de test. Toute PR garde vertes les suites existantes.

### 9. Écrans

Aucun emoji, icônes `lucide-react`, tokens de `.claude/design-system.md`. Libellés de statut de
demande de pièce importés de `shared/constants/part-requirements.ts`.

### 10. Branches, worktrees et fusion

- Branche de base découverte, pas supposée (aujourd'hui `main`).
- Branches `lot/<rôle>/<T-id>-<slug>`, une branche par PR.
- Un worktree par agent, à côté du dépôt : `../fm-<rôle>-<n>` (ex. `../fm-be-1`), avec son propre
  `node_modules` et sa propre branche Neon de test.
- Rebase sur la branche de base avant relecture ; jamais de fusion de la base dans une branche de
  lot.
- Fusion une PR à la fois : rebase, `npm run check` global à zéro erreur, `npm test`,
  `test:integration`, `test:contract`, approbation du relecteur, squash merge. Une étape rouge sort
  la PR du train.
- PR de moins de 400 lignes hors tests, avec la section « RAIDER review » et la commande de preuve.
- Messages de commit et PR sans mention d'outil ni d'assistant.

### 11. Réutilisation

Avant toute brique non triviale : chercher dans le dépôt, puis dans les paquets déjà installés,
puis en open source. La PR note le choix en une ligne : **Adopt / Adapt / Learn / Build**.

Briques existantes à réutiliser, jamais à réécrire :

| Besoin | Brique |
|---|---|
| Tableau de liste | `PremiumDataTable` (`client/src/components/design-system/premium-data-table.tsx`) |
| Brouillon de formulaire | `useFormDraft` + `createFormDraftStorage` (AGENTS.md §6) |
| Bouton qui écrit de l'argent ou du stock | `useSingleFlightMutate` (`client/src/hooks/use-single-flight.ts`) |
| Erreurs | `AppError` côté serveur, `userMessageOf` côté client |
| Logs | `moduleLogger` (`server/lib/logger.ts`) |
| Cloison client | `canAccessOwned`, `ownerScopeOf` (`server/lib/client-scope.ts`) |
| Fichier téléversé | `uploadedFileCandidates` (`server/lib/uploaded-file.ts`) |
| Alertes | fonctions publiques de `server/services/alert-service.ts` |
| Rôles, libellés de statut | `shared/constants/roles.ts`, `shared/constants/part-requirements.ts` |
| Exports PDF et Excel | `jspdf`, `xlsx` (déjà installés) ; `docx` ajouté en T-02 |
| Captcha | `altcha-lib` (Adopt : open source, auto-hébergé, sans service tiers) |

Les capacités neuves du lot sont **génériques et configurées**, pas codées pour un cas :

- `auditWrites(config)` : table déclarative chemin → entité, pas une ligne de code par route.
- `loginLockoutGuard` : seuil et durée en configuration (défaut D-06 : 5 échecs, 15 min).
- Tâches de fond : un seul exécutant avec verrou consultatif, chaque tâche n'apporte que sa
  fonction.
- Exports : un générateur commun (colonnes déclarées, format choisi), chaque export ne déclare
  que ses colonnes et sa requête.
- Drapeaux : une table unique (§6).

Règle : un même code écrit deux fois devient une fonction commune dans la PR qui fait la seconde
copie.

### 12. Standard RAIDER

Tout travail du lot respecte le standard RAIDER (source : `EagleFox31/project-registry`,
`RAIDER.md`). Ce que chaque principe exige ici :

| Principe | Exigence dans le lot |
|---|---|
| **R — Reusable** | Capacités génériques configurées (§11) ; pas de `if` sur un cas quand une config suffit. |
| **A — Agnostic** | Branche de base, port, URL de base, base de test lus dans l'environnement ou découverts, jamais écrits en dur ; pas de chemin propre à une machine dans le code. |
| **I — Idempotent** | Migrations rejouables (§5) ; une tâche de fond relancée ne crée pas de doublon ; un second appel d'une même transition ne réécrit rien. |
| **D — Non-régressif** | Les contrats existants (routes, formats, libellés, événements) restent verts ; les suites existantes passent toutes (§8, §10). Une rupture se versionne et se documente. |
| **Failure memory** | Lire `docs/analysis/LESSONS_LEARNED.md` avant de toucher une zone à incident connu ; toute erreur ou quasi-incident y est consigné (cause, prévention vérifiable, leçon). Une erreur répétée exige un contrôle automatique. |
| **E — Engineering-grade** | Contrat d'erreur (§3), moindre privilège (refus par défaut des rôles), aucun secret dans les logs, Adopt / Adapt / Learn / Build noté (§11), gates proportionnels à la surface touchée. |
| **R — Retroactive** | Données existantes préservées : aucune suppression ni réinitialisation ; les données de recette (véhicule #13, pièce #20, OT #62, demande #7, commande #5, facture #39, règlement #4) ne se suppriment que sur confirmation explicite. |

Toute dérogation est écrite dans « Écarts » ci-dessous ou dans la PR, jamais cachée dans le code.

**Definition of Done d'une tâche** : avant de la déclarer finie, l'agent passe la liste R, A, I, D,
failure memory, E, gates proportionnels, reuse-first, R, et indique dans la PR (section « RAIDER
review ») ce qui est couvert, ce qui ne s'applique pas et pourquoi. Pas de « terminé » sans la
commande de preuve et sa sortie.

### 13. Journal de travail par agent

Chaque agent tient **son propre fichier** `docs/journal/<agent>.md` (convention et modèle :
`docs/journal/README.md`). Un fichier par agent : pas de conflit de fusion entre agents.

- Une entrée par commit, ajoutée **dans le même commit** que le changement.
- L'entrée dit **quand** (horodatage avec fuseau), **quoi** (T-id, branche, commit), **comment**,
  **pourquoi**, et **comment tester** : prérequis, étapes, résultat attendu, commande de preuve.
  Cette dernière partie est celle que la QA rejoue.
- Les entrées ne se réécrivent pas : une correction ajoute une entrée qui renvoie à la précédente.
- Retrouver qui a fait quoi : `grep -rn "T-11a" docs/journal/`.
- Un incident se consigne dans `LESSONS_LEARNED.md` ; le journal y renvoie sans le recopier.

## Écarts par rapport au plan initial

- **P-23, e-mail : coupé.** T-46 est retiré du lot. Le contrat des préférences garde le champ
  `email` (ajout futur sans rupture), mais l'écran ne l'affiche pas et le serveur l'ignore tant que
  `email-notifications` est coupé.
- **P-08, contraintes d'exclusion (T-23c)** : elles exigent l'extension `btree_gist`. Si Neon ne la
  fournit pas, la garde applicative `bookingGuard` reste seule, et l'écart est consigné ici.
- **Export client** : lundi, un client reçoit 403 sur tous les exports ; l'export filtré sur ses
  propres lignes vient au lot suivant.
- **CI à impact (`appfactory-project-automation`) : non adoptée ce week-end.** Le dépôt n'a pas
  de CI de tests (seul `build-android-apk.yml`). Installer une CI pendant le lot ajoute un risque
  sans gain avant lundi : les gates tournent dans le train de fusion (§10). Adoption prévue après
  la recette.
- **Contrats (T-02, T-03), écarts au plan** :
  - réception d'une pièce (P-16) : **pas de route `POST …/receive`**. La transition existante
    `PATCH /api/part-requirements/:id` attribue déjà `receivedBy` (session de tests, 30 octobre) ;
    une seconde route doublerait la règle. Le lot ajoute `receivedAt` et l'affichage ;
  - 409 de double affectation : les chevauchements partent dans un champ `conflicts`, pas dans
    `errors` (réservé aux erreurs de champ `{ field, message }`). Avec `lockedUntil` du 429, cela
    demande à T-08 un ajout non cassant : `AppError` accepte des `details` fusionnés dans le corps ;
  - `msw` en 2.x : la 3.x exige TypeScript 5.9, le dépôt est en 5.6 ;
  - `nodemailer` non ajouté (e-mail coupé, P-23) ;
  - ACF et agrément PD sans durée de validité fixe (`validityMonths = null`) : à confirmer par le
    client.

## Conséquences

- Les agents peuvent travailler en parallèle sur les contrats dès M0, sans attendre l'API.
- Les fichiers chauds (`shared/schema.ts`, `server/api/index.ts`, `client/src/App.tsx`, menu,
  `useRealTimeSync.ts`) sont pré-câblés une seule fois, par leur propriétaire ; les PR de
  fonctionnalité ne touchent ensuite que leurs propres fichiers.
- Une fonctionnalité non finie au gel reste cachée par son drapeau, sans code mort visible.
- Coût : la discipline de propriété ralentit une correction transverse, qui doit passer par le
  propriétaire du fichier.

## Amendement du 1er novembre 2026 : retrait du captcha (P-26)

Décision du responsable produit : le captcha à la connexion est jugé disproportionné pour
une application interne. Il est retiré : garde `captchaGuard`, route `GET /api/auth/challenge`,
widget ALTCHA, drapeau `captcha`, dépendances `altcha` et `altcha-lib`.

- Le verrouillage par nom saisi (P-03, `loginLockoutGuard`) reste en place sur
  `POST /auth/login` et `POST /auth/pin-login`.
- Un `FEATURE_FLAGS` qui contiendrait encore `captcha=on` est ignoré (clé inconnue, journalisée).
- Non-régression : `tests/contract/login-guards-mount.contract.test.ts` vérifie qu'après
  3 échecs le bon mot de passe connecte, et que la route de défi n'existe plus.
- Les mentions du captcha plus haut dans cet ADR décrivent l'état d'origine.
