## Vidéo de démonstration du chauffeur : le logisticien programme, l'atelier reçoit la panne

**Quoi** : `e2e/demo/10-chauffeur.spec.ts` est réécrite en trois contextes de rôles (logisticien, chauffeur, chef d'atelier). Le logisticien programme la mission par l'assistant (camion `DEMO-JOUR-001`, remorque `DEMO-REM-001`, chauffeur) puis fixe les budgets (carburant, frais de route, imprévus) ; le chauffeur se connecte avec son PIN, voit la mission du jour et confirme le départ ; il déclare une panne grave ; le chef d'atelier, déjà connecté, reçoit l'alerte puis voit la panne dans « Pannes déclarées ». Le seed `seedDriverDay` ne crée plus de mission (c'est le logisticien qui la crée), pose le PIN du chauffeur et nettoie les pannes et OT de panne du camion de démo.
**Comment** : base Postgres locale dédiée `fleet_test_demo_chauffeur` (garde `assertLocalDatabase`), serveur local sur cette base, 1920x1080. Assertions dures en base : affectation (camion, remorque, chauffeur), budgets enregistrés, mission `in_progress`, panne créée sur le camion de la mission. Preuve temps réel : la trame WebSocket `incident_reported` (entityId de la panne) reçue par la session du chef d'atelier. Montage : même pipeline que les autres profils, voix Guillaume, débit 0,88, sous-titres 52 px, -15 LUFS.
**Pourquoi** : la vidéo chauffeur était solo (mission du jour, départ) ; elle ne montrait ni qui programme la mission, ni ce qui arrive à l'atelier quand une panne est déclarée.
**Preuve** : `E2E_DEMO=1 node node_modules/@playwright/test/cli.js test e2e/demo/10-chauffeur.spec.ts` (verte, base locale) ; `npm run check` (0 erreur TS) ; tests unitaires : seuls 2 échecs d'environnement dans `db-pool-options` (driver installé), identiques sans ce changement.
