## Appli chauffeur hors ligne, V5b-1b : la clé d'une panne est libérée quand rien n'a été écrit

**Quoi** : (1) `createIncident` convertit un échec antérieur à la validation (lecture du périmètre, transaction) en `AppError(503, ..., { code: "INCIDENT_WRITE_FAILED" })` ; (2) un véhicule inexistant donne 404 `INCIDENT_VEHICLE_NOT_FOUND` pour tout type de signalement (le retard et l'autre passaient par la clé étrangère, un 500) ; (3) les deux codes rejoignent `PRE_WRITE_REFUSAL_CODES` : la clé est libérée ; (4) le 409 « en cours » ne promet plus que la panne apparaîtra ; (5) leçon dans `LESSONS_LEARNED.md`.
**Comment** : contrats d'abord, lancés avant tout correctif : 4 échecs sur 13 (réessai après échec de transaction : 500 au lieu de 503 et clé gardée ; véhicule inexistant sans OT : 500 ; avec OT : 404 mais clé gardée ; message du 409). Les contrats « même clé, deux comptes » et « lecteur refusé » passaient déjà : ils figent le comportement. Les codes sont aussi ajoutés à `ApiErrorCode`, `STATUS_MESSAGES` et `TYPE_BY_CODE` (champs optionnels, contrat inchangé).
**Pourquoi** : sinon une panne transitoire côté serveur bloquait la déclaration du chauffeur pendant 7 jours derrière un 409 trompeur. Une 5xx reste normalisée en `INTERNAL` pour le client par la garde de sortie ; le code dédié ne sert qu'à libérer la clé.
**Preuve** : `node ../lot-tools/db-lock.mjs v5b-1b -- node node_modules/vitest/vitest.mjs run --config vitest.contract.config.ts tests/contract/idempotency-driver-breakdown.contract.test.ts` ; unitaires `incident-service`, `idempotency-guard`, `leak-check-hygiene`.
