## Appli chauffeur hors ligne, lot V5b-1 : la panne se rejoue sans doublon

**Quoi** : (1) `POST /api/driver/breakdowns` entre dans `IDEMPOTENCY_ROUTES` (`staleSeconds: null`, `keepKeyOnUncertainOutcome`) : un rejeu avec la même `Idempotency-Key` renvoie la même réponse (même incident, même OT), deux requêtes simultanées n'en exécutent qu'une ; (2) le 409 « en cours » du garde porte `code: "IDEMPOTENCY_IN_PROGRESS"` (ajouté à `ApiErrorCode`, `STATUS_MESSAGES` et `TYPE_BY_CODE` côté client) ; (3) drapeau `driver-offline` déclaré, désactivé par défaut, qui exige `offline-writes` ; (4) le plan `docs/plans/v5b-chauffeur-hors-ligne.md` est livré avec cette PR.
**Comment** : test rouge d'abord. Le contrat `tests/contract/idempotency-driver-breakdown.contract.test.ts` a été lancé avant tout correctif : 4 échecs sur 7 (rejeu : pas d'en-tête `Idempotent-Replayed` ; autre corps : 201 au lieu de 422 ; concurrence : 2 incidents et 2 OT au lieu d'1 ; statut en concurrence : code `CONFLICT` au lieu de `IDEMPOTENCY_IN_PROGRESS`). Le correctif tient en une entrée de configuration et un `code` : le garde atomique existant (`reserve`) fait l'exclusion, rien n'est ajouté dans la route.
**Pourquoi** : en hors ligne, le téléphone rejoue la même requête après une réponse perdue ; sans clé, le chauffeur créait un second incident et un second OT d'atelier. Le code distingue pour le client un « en cours, réessayer plus tard » d'un vrai conflit métier.
**Preuve** : `node node_modules/vitest/vitest.mjs run --config vitest.contract.config.ts tests/contract/idempotency-driver-breakdown.contract.test.ts` (7 sur 7 après correctif, 3 sur 7 avant) ; unitaires `tests/unit/server/idempotency-guard.test.ts` et `cdc-skeletons.test.ts`.
